The per-place file shape

Every place folder under components/places/<name>/ has the same files:

  • <name>-world.ts — the procedural 3D world: layout, anchors, palette, factory function
  • <name>-scene.tsx — scene-level React component that calls the world factory
  • <name>-experience.tsx — the next/dynamic import wrapper with controls UI
  • <name>-story.tsx — editorial content (story, features, stats, etiquette, FAQs)
  • <name>-world.test.ts — Vitest tests on layout/anchor helpers

Data files live separately

lib/data/<name>.ts holds the editorial content — separate from the 3D world:

  • FEATURES[] — hotspots with id, title, Marathi name, blurb, full detail
  • STATS[] — labelled facts
  • STORY[] — narrative sections
  • ETIQUETTE[] — visitor guidance
  • FAQS[] — Q/A pairs

Feature ids in the data file double as hotspot ids in the 3D world — one source of truth.

Rendering Model — SSR Shell + 3D Client Island

The core architectural decision: WebGL stays on the client. The server renders the editorial shell as fast HTML; the 3D scene mounts only when the client reaches it.

What the server renders

  • The place cover — name, category badge, metadata
  • The story sections — headings and body text
  • The stats — labelled facts about the place
  • The etiquette — visitor do's and don'ts
  • The FAQs — questions and answers
  • The practical info — how to reach, tips, nearby places

All of this is in the initial HTML. Google sees it. A visitor on a slow connection sees it immediately. A screen reader reads it.

What the client renders

  • The canvas element — mounted via next/dynamic with ssr: false
  • The 3D scene — procedural geometry, instanced meshes, lights, sky shader
  • The interaction layer — orbit controls, zoom, hotspot flight, mode toggles
  • The three.js dependency — one shared bundle, loaded once

This chunk downloads only when the visitor reaches a place page and the component mounts. A bot crawling the site never downloads it.

Why this split matters: SEO works because the editorial content is in the HTML. Accessibility works because the canvas is aria-hidden and the text content is real DOM. Performance works because the 3D JS is not in the critical path. Error isolation works because if WebGL fails, the story still renders.

The factory pattern

Every world module exports a factory function — create<Name>World(container, options) — that:

  • Creates the THREE.WebGLRenderer and attaches it to the container
  • Builds the scene graph — ground, props, lights, sky — from the layout
  • Returns an EmpressWorld-shaped object that the experience component holds and calls
  • Accepts callbacks — onSelect, onHover, onReady — so the UI layer stays separate

The track() helper pushes every disposable (geometry, material, mesh) onto a disposables array so dispose() tears them all down in one pass — no WebGL context leaks across React remounts.

Shared Infrastructure — The Diorama Core

Every place shares one small module — diorama-core — for sky, palette, markers, and math helpers. Everything else is per-place.

What the core provides

  • Sky shader — a custom GLSL sky dome with sun-direction blending. Every place with a sky uses the same shader.
  • Palette type — a plain data object (sky colours, sun, lights, fog, exposure) that every place's palette function returns.
  • Time-of-day type — 'dawn' | 'golden' | 'dusk' — shared across all scenes.
  • Sprite helpers — markerSprite() and radialSprite() for hotspot markers and lamp flames.
  • Math helpers — clamp, damp, smoothstep, and mulberry32 (deterministic seeded PRNG).
  • WebGL check — supportsWebGL so the client can degrade gracefully.

Why this matters

  • Consistency — every scene has the same sky shader, marker style, and palette model.
  • Testability — palette functions are pure data-returning functions. Vitest tests them without a canvas.
  • Extensibility — adding a new time-of-day variant means one union member and one palette object. No shader change.
  • Determinism — mulberry32(seed) makes every layout reproducible. Same seed, same tree positions, same camera anchors. Tests can assert on exact prop positions.

Case Study: Empress Garden 3D World (1,032 lines)

The most complete 3D world in the project. Built from layout constants → seeded prop placement → terrain → materials → instanced meshes → lights → render loop. No imported assets.

36 trees (3 canopy spheres each = 108) 42 rose bushes (blooms + foliage) 6 flower-show tents 11,660 terrain vertices 0 textures 3 palettes 1 directional light + 1 hemisphere ~190 instanced objects

What makes this procedural approach testable

  • buildEmpressLayout(seed) returns a plain object — Vitest asserts on prop count, positions, feature ids.
  • getEmpressAnchors() returns a record of plain arrays — test each feature id maps to an anchor.
  • getEmpressPalette(t) returns a Palette object — test the shape and values.
  • Zone predicates (inLawn, inRose, etc.) return booleans — test at boundary points.

What the procedural approach saves

  • No artist — one developer writes the geometry. No Blender, no GLTF export, no texture authoring.
  • No asset weight — the entire Empress scene is generated from ~1,000 lines of TypeScript. No GLB download.
  • Fast iteration — change a tree count, a rose-ring radius, or a tent position by editing one number in a helper.
  • Reproducibility — same seed, same layout. Camera anchors are stable. Tests are deterministic.

Camera System — Anchors, Home View, Hotspot Flight

Every feature hotspot has a defined camera anchor — a target point, a viewing direction, and a distance. Tapping a hotspot interpolates the camera to that position so the transition feels like moving through the space.

Anchor anatomy

Each feature hotspot has a camera anchor — three values that define where the camera goes when the user taps it:

  • target — the world-space point the camera looks at (e.g. the rose garden centre, the temple doorway)
  • direction — the normalized look vector, used for orbit constraints so the camera can't point through the ground
  • distance — how far the camera sits from the target (wide establishing shot vs. close-up detail)

Anchors are built once at module load time, not every frame. They're stable and testable.

The flight behaviour

  • When setActive(id) is called, the camera interpolates from its current spherical coordinates to the anchor's target + distance + phi + theta.
  • The interpolation is smooth — the viewer feels like they are moving through the space, not jumping between photos.
  • When the camera arrives, onSelect fires and the feature story surface appears in the UI.
  • resetView() returns the camera to the home position — the establishing shot of the whole garden.
Design intent: the camera system exists to make the 3D scene feel like a walkthrough, not a slideshow. Each hotspot has a purpose — a specific viewpoint that reveals something about the place. The numbering on the diorama tells the visitor what to look at; the flight tells them how to see it.

Lighting & Palette System — Three Moods Per Place

Every heritage place has 2–3 time-of-day palettes. A palette is a plain data object — the world module reads it to reconfigure the sky, the sun, the fog, and the exposure.

The lighting rig (every scene)

  • HemisphereLight — sky colour → ground colour. Soft fill, no shadows. Intensity from the palette's ambient.
  • DirectionalLight (sun) — colour from sun, intensity from sunIntensity. Casts shadows. 2048×2048 shadow map, 80-unit frustum.
  • Sun direction — computed from azimuth + elevation every frame. The sun disc and the sky horizon both respond to this vector.
  • Fog — distance-based, colour from the palette. Hides the ground-plane edges.

The sky shader

A custom GLSL shader — SKY_VERT / SKY_FRAG — renders a BackSide sphere (radius 420) as the sky dome. It blends topColor and bottomColor by vertical position, then tints the horizon by the sun direction — a cheap atmospheric-scattering approximation that reads well at diorama scale.

On palette change, the shader uniforms are updated — sky colours, sun colour, sun direction. No geometry rebuild. The sky transitions smoothly because the uniforms are lerped each frame.

Data Layer — The Dual-Driver Database

One small module — lib/store/db.ts — backs every data operation. Three drivers, chosen at runtime from environment variables. Write operations are serialised through a single queue.

Driver selection logic

  • If Redis credentials are present (KV_REST_API_URL + token, or UPSTASH_REDIS_REST_*), the Redis driver is used — this is production on Vercel with a connected store.
  • If running on Vercel but no credentials are present, the unconfigured driver is used — reads return empty (pages still render), writes throw a clear error that points to DEPLOYMENT.md. This is fail-closed: a read-only filesystem never throws an opaque EROFS.
  • Otherwise (local dev, self-hosting), the file driver is used — data/db.json on disk, with atomic write-then-rename for crash safety.

The write queue

Every mutate() call goes through a single promise chain — read, apply the mutator, write. This serialises writes within one process, so two concurrent mutations can't interleave.

The trade-off is explicit: across Vercel serverless instances (multiple cold starts), the queue is per-instance — two instances can still race. At this app's write volume, the team has chosen simplicity over distributed consistency. A real Redis queue would be the next step if write volume grows.

Fail-closed design: on Vercel without Redis, writes throw a clear error rather than dying silently on a read-only filesystem. Reads degrade to empty so the site still serves — the review and suggest features just don't persist. This is a deliberate choice: a degraded site is better than a broken one.

Upload API — Community Photo Storage

app/api/uploads/route.ts handles multipart photo uploads from the community. Two storage backends, chosen at runtime — Vercel Blob for production, local disk for dev.

What the API accepts

  • Multipart form data, field name files — the browser submits a FormData body
  • Up to 6 photos per request, each up to 4 MB
  • Accepted types: JPG, PNG, WEBP, GIF — anything else is rejected before any write
  • Validation happens first, across the whole batch — a bad file late in the batch can't leave half the uploads persisted

Where photos go

  • Vercel Blob — when BLOB_READ_WRITE_TOKEN is set, @vercel/blob put() stores the file with access: 'public' and returns a public URL
  • Local disk — otherwise, /public/uploads/ for next dev and self-hosting, with the file served as a static asset
  • Filename — {timestamp-in-base36}-{uuid-slice}.{ext}, collision-resistant and sortable by time, no user data in the name
Design intent: the upload API is the seam where community content enters the system. It is deliberately simple — multipart, validated first, dual-storage — so it works on Vercel (cloud), on next dev (local disk), and on any self-hosted Node host. The 4.5 MB Vercel function body limit is documented as a known ceiling; the constants are sized so local uploads work fully and Vercel uploads cap naturally.

Environment Variables — Configuration Resolution

The entire deployment model is driven by environment variables. One codebase runs locally, on Vercel preview, and on Vercel production — the right driver for each, chosen at runtime.

Why this resolution matters

A fresh deploy never advertises localhost. If the maintainer sets NEXT_PUBLIC_SITE_URL explicitly, that wins — useful for a custom domain. Otherwise, Vercel's injected NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL gives production a stable domain across deploys, and NEXT_PUBLIC_VERCEL_URL gives each preview a self-consistent URL.

This is why a preview deployment of a new place's 3D scene has correct links and metadata — no manual config per deploy.

Credential detection

Redis detection accepts both Vercel's injected KV_REST_API_* names and Upstash's own UPSTASH_REDIS_REST_* names — so the app works whether the store was provisioned through the Vercel integration or directly. The same dual-acceptance pattern applies to Blob.

The VERCEL env var is a boolean injected by Vercel at runtime — it is the signal that distinguishes production (where the file driver is skipped) from local (where the file driver is the default).

Testing Strategy — Vitest on Pure, Canvas-Free Helpers

The project's tests live on the pure, WebGL-free helpers — layout builders, zone predicates, anchor generators, palette functions. WebGL is hard to test headless, so the architecture isolates the testable bits.

What's tested (per place)

  • Layout builder — build<Name>Layout(seed) returns the right prop count, with props at expected positions
  • Zone predicates — inLawn, inRose, inGreenhouse, etc. return the right bool at boundary points
  • Anchor generator — get<Name>Anchors() maps each feature id to an anchor with the right target, direction, distance
  • Palette function — get<Name>Palette(t) returns a Palette object of the right shape and values
  • Home view — get<Name>HomeView() returns the expected camera position

What's not unit-tested (by design)

  • The WebGL path — create<Name>World(container, options), the render loop, the shadow map, the sky shader, instanced mesh setup, sprite flames
  • These are covered by manual visual inspection: open the page, orbit, click hotspots, toggle modes, and verify the scene looks right
  • Automated canvas tests would be fragile and high-maintenance — not worth it at this stage

The test philosophy: if a function can be tested without a canvas, it should be. The 3D scene construction is the integration layer — tested by eye, not by assertion.

Performance Characteristics

The scene is procedurally generated once on mount, then drawn every frame — no per-frame layout rebuild. The heaviest per-frame cost is the shadow map render.

What's in the Empress scene

ElementCountTechnique
Ground plane1120×116, 11,660 verts, vertex colours per zone
Tree trunks36InstancedMesh, 1 cylinder geometry
Tree canopies108InstancedMesh, 1 icosahedron, 3 per tree
Rose blooms42InstancedMesh, 1 sphere geometry
Rose foliage42InstancedMesh, 1 sphere geometry
Greenhouse1Box geometry + glass material
Show tents6Cone geometry (canvas + stripe)
Lamp posts4Cylinder + sprite flame
Benches4Box geometry
Lamp flames4Sprite, additive blending

Total instanced objects: ~190. Zero textures. All materials are colour + roughness (+ metalness for a few).

What keeps it performant

  • Instancing — one geometry draw call serves many objects. 36 trees = 2 draw calls (trunks + canopies), not 36.
  • Vertex colours — ground is coloured per zone in the vertex buffer, no texture look-up.
  • One light + one shadow map — only the directional sun casts shadows. Hemisphere fill is shadow-free.
  • Fog — hides the ground edges, reducing pixel fill at the borders.
  • Pixel ratio cap — no 3× retina rendering. On a 3× phone, the canvas renders at 2× max.
  • No textures — every material is a colour + roughness. No texture download, no GPU texture memory.
Cost model: build once on mount, draw every frame. The heaviest line is the 2048×2048 shadow map — one directional light, one frustum. On a modern phone this is smooth. On a low-end device, the pixel ratio cap and fog keep it tolerable. The trade-off is explicit: the scene is a diorama, not a high-fidelity replica, and the performance budget matches that choice.

Extension Points — How to Add a New Place

To add a new heritage place — say, Shivneri Fort — you follow this path. Each step is isolated; you don't touch any existing place.

Why each step is isolated

  • The data file (Step 1) is pure content — it imports nothing 3D. It can be written and reviewed independently.
  • The world module (Step 2) imports three.js, diorama-core, and optionally its own data file. It does not import any other world or any React.
  • The story (Step 3) imports the data file. The experience (Step 3) imports the world module. Neither imports any other place's code.
  • The catalog registration (Step 4) adds one entry to an array. It does not touch any existing entry.

What this enables

  • Parallel work — two developers can work on different places at the same time without merge conflicts in the 3D code.
  • Safe deletion — removing a place means deleting one folder and one catalog entry. No other file breaks.
  • Reviewable increments — a pull request for one new place touches only that place's files plus the catalog. The diff is small and reviewable.
  • Reusability — the folder pattern is documented by example. A new contributor copies an existing place folder and adapts it.

Deployment Topology — One Codebase, Three Environments

The same code runs locally, on Vercel preview, and on Vercel production — the right driver for each, chosen at runtime from environment variables.

Why Vercel works well

  • Next.js 16 is first-class on Vercel — no custom server, no Dockerfile.
  • Upstash Redis is integrated via Vercel's KV — one credential pair.
  • Vercel Blob is integrated the same way — upload token, no S3 wrangling.
  • Preview deployments give every push a live URL — useful for reviewing a new place's 3D scene before merging.

What changes at scale

  • Redis — at high write volume, a per-instance write queue isn't enough. Move to a Redis-based queue (Upstash QStash, or a Redis list with LPUSH/BRPOP).
  • Blob — at high upload volume, switch to @vercel/blob/client upload() for streaming past the function body limit.
  • Region — if the audience shifts outside India, pin the Vercel project to a closer region.
  • CDN — the 3D bundles are already served via Vercel's edge. No separate CDN needed until the bundle grows past a few hundred KB.

Architecture Summary

What was built

  • A Next.js 16 + React 19 web app that guides visitors through Pune's heritage sites.
  • 15 places, each with editorial depth (story, etiquette, FAQs, Marathi names) and a hand-built procedural 3D diorama.
  • A dual-driver data layer — Redis for production, file for dev, fail-closed when unconfigured.
  • A file upload API — Vercel Blob or local, for community photos.
  • A per-place component architecture with a shared diorama core.

What makes it technically distinctive

  • Procedural 3D at scale — 15 places, zero imported meshes, every vertex generated from TypeScript.
  • SSR + client island — editorial content is server-rendered; 3D is a dynamic import that loads on demand.
  • Deterministic layouts — seeded PRNG makes every world reproducible. Tests assert on exact prop positions.
  • Environment-driven deployment — one codebase runs locally, on preview, and on production with the right driver for each.
  • Testable 3D — the parts that matter are pure functions, tested without a canvas.
The core idea, restated: ExplorePune is a city guide where every place is a diorama you can orbit, zoom, and fly through — built entirely from code, with editorial depth, and deployed for free on Vercel. The architecture supports adding more places without an art pipeline, without heavy assets, and without a backend beyond a Redis document store. The procedural approach is not just cheaper — it makes the project viable at a bootstrapped budget, and it keeps the cost of adding places low forever.

The 5 architectural pillars

The key trade-offs

  • No auth, no accounts — anonymous reviews and suggestions. The next step if community volume grows.
