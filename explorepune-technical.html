The per-place pattern

Every place under components/places/<name>/ follows the same file shape:

  • <name>-world.ts — procedural 3D world module (layout, anchors, palette, create<Name>World())
  • <name>-scene.tsx — scene-level React component that calls the world factory
  • <name>-experience.tsx — the next/dynamic import wrapper + controls UI
  • <name>-story.tsx — editorial content imported into place-detail.tsx
  • <name>-world.test.ts — Vitest tests on layout/anchor helpers (no canvas required)

What about the data files?

lib/data/<name>.ts holds the editorial content for each place — separate from the 3D world:

  • FEATURES[] — hotspots with id, title, Marathi name, blurb, full detail
  • STATS[] — labelled facts
  • STORY[] — narrative sections
  • ETIQUETTE[] — visitor guidance
  • FAQS[] — Q/A pairs

Feature ids in the data file double as hotspot ids in the 3D world — a single source of truth.

Rendering Model: SSR Shell + 3D Client Islands

The core architectural decision: keep WebGL out of the server render. Every 3D page uses next/dynamic with ssr: false so the canvas only mounts client-side.

Server-rendered shell

app/places/[slug]/page.tsx runs on the server — it fetches the place data, renders the cover, category badge, story headings, stats, etiquette, and FAQs. The first paint is fast HTML + CSS.

The 3D <Experience> component is a next/dynamic import:

// app/places/[slug]/page.tsx (conceptual)
import dynamic from 'next/dynamic';

const Experience = dynamic(
  () => import('@/components/places/place-detail')
    .then(m => m.PlaceDetailExperience),
  { ssr: false }
);

export default PlacePage({ params }) {
  return (
    <div>
      <Cover ... />
      <Story ... />
      <Experience place={place} />
      <Etiquette ... />
      <FAQs ... />
    </div>
  );
}

Client-side 3D island

When the client hydrated and the dynamic import resolves, Experience mounts a <canvas> and calls create<Name>World(container, options). From that point, everything is WebGL.

This split has several benefits:

  • SEO: the editorial content is in the initial HTML — Google sees the story, FAQs, Marathi names.
  • Accessibility: the aria-hidden="true" on the canvas doesn't block screen readers from the text content.
  • Performance: no JS bundle for 3D is sent to bots or users who never scroll to the canvas.
  • Error isolation: if WebGL fails (older device, strict privacy settings), the text content still renders.
Next.js config: next.config.ts should leave the default swcMinify and allow the three.js bundle through. Nothing exotic — Next.js 16 handles the next/dynamic + client component split out of the box.

Shared Infrastructure: diorama-core.ts

The components/places/three/diorama-core.ts module is the only 3D code that every place shares. Everything else — layout, props, materials — is per-place.

What's in diorama-core

  • Sky shader — SKY_VERT / SKY_FRAG: a custom GLSL sky dome with sun-direction blending. Used by every place with a sky.
  • Time-of-day types — TimeOfDay = 'dawn' | 'golden' | 'dusk' — and Palette type: skyTop, skyBottom, sun, sunIntensity, hemiSky, hemiGround, ambient, fog, lantern, sunAzimuth, sunElevation, exposure.
  • Palette helpers — getEmpressPalette(t) returns one of three palettes. Other places have their own palette functions following the same pattern.
  • Sprite helpers — markerSprite() and radialSprite() for hotspot markers and lamp flames.
  • Math helpers — clamp, damp, smoothstep, mulberry32 (deterministic seeded PRNG).
  • WebGL support check — supportsWebGL export so the client can degrade gracefully.

Why this matters

  • Consistency: every scene has the same sky shader, the same marker style, the same palette model.
  • Testability: palette functions are pure — they return a Palette record. No WebGL, no canvas. Vitest can test them directly.
  • Extensibility: adding a new time-of-day variant means adding one entry to the Palette type and one palette object — no shader change.
  • The PRNG: mulberry32(seed) is the reason layouts are deterministic. buildEmpressLayout(seed = 1892) always returns the same 36 trees at the same positions — which means camera anchors are stable and tests are reproducible.

Prop layout (deterministic seeded)

// buildEmpressLayout(seed = 1892) — 36 trees, 42 roses, 6 tents
export function buildEmpressLayout(seed = 1892): {
  props: EmpressPropSpec[];
  propCount: number;
  markerBases: Record<FeatureId, { x, y, z }>;
  treeCount: number;
  roseCount: number;
  tentCount: number;
} {
  const rnd = mulberry32(seed);
  const props: EmpressPropSpec[] = [];
  const push = (p: EmpressPropSpec) => props.push(p);

  // 36 old-growth trees — rejection-sampled into the grove ring
  let guard = 0;
  const trees: { x, z, s }[] = [];
  while (trees.length < 36 && guard < 5000) {
    guard++;
    const x = (rnd() - 0.5) * 84;
    const z = (rnd() - 0.5) * 80;
    const r = Math.hypot(x, z);
    if (inLawn(x, z) && r < 12) continue;
    if (inRose(x, z)) continue;
    if (inGreenhouse(x, z)) continue;
    if (inShowGround(x, z)) continue;
    if (r < GROVE.rInner - 2) continue;
    if (r > GROVE.rOuter) continue;
    if (trees.some(t => Math.hypot(t.x - x, t.z - z) < 5.6)) continue;
    trees.push({ x, z, s: 1.05 + rnd() * 0.7 });
  }
  // ... roses, lamps, benches, tents follow the same pattern
}

Terrain, Materials & Instancing

Terrain: vertex-displaced plane

// 120×116 plane, subdivided 110×106 — 11,660 vertices
const groundGeo = track(new THREE.PlaneGeometry(120, 116, 110, 106));
groundGeo.rotateX(-Math.PI / 2);
const pos = groundGeo.attributes.position as THREE.BufferAttribute;
for (let i = 0; i < pos.count; i++)
  pos.setY(i, terrainHeight(pos.getX(i), pos.getZ(i)));
groundGeo.computeVertexNormals();

// terrainHeight() — multi-zone height field
export function terrainHeight(x: number, z: number): number {
  let h = 0.12 * Math.sin(x * 0.09) * Math.cos(z * 0.08);
  if (inLawn(x, z)) h = 0.04 * Math.sin(x * 0.2) * Math.cos(z * 0.18);
  if (inRose(x, z)) h = 0.08;
  if (inGreenhouse(x, z)) h = 0.22;
  const outside = Math.max(Math.abs(x), Math.abs(z)) - 52;
  if (outside > -1) h -= 16 * smoothstep(-1, 6, outside);
  return h;
}

The terrain receives vertex colours per zone — lawn greens, rose-bed browns, show-ground dust — so the ground reads as distinct areas without texture maps.

Camera System: Anchors, Home View & Hotspot Flight

Anchor definitions

Each feature hotspot has a camera anchor — a target point, a look direction, and a distance. These are built once at module load and reused for every flight.

               dir: [number, number, number];

> {
  return {
    'old-canopy':    { target: [22, 3, -14], dir: [0.55, 0.4, 0.73], distance: 26 },
    'rolling-lawns': { target: [0, 0.4, 0],   dir: [0.12, 0.55, 0.83], distance: 32 },
    'rose-garden':   { target: [ROSE.x, 0.6, ROSE.z], dir: [-0.5, 0.42, 0.76], distance: 18 },

target = where the camera looks at (world space).
dir = normalized look direction (used for orbit constraints).
distance = how far the camera sits from the target.

OrbitControls (conceptual)

The camera is an OrbitCamera (a spherical-coordinate wrapper around PerspectiveCamera):

  • radius — distance from target (scroll to zoom in/out)
  • phi — polar angle (drag up/down)
  • theta — azimuth (drag left/right)
  • Constraints: min/max radius, min/max phi so the user can't orbit through the ground or zoom into the sun

When setActive(id) is called, the camera spherical coordinates interpolate to the anchor's target+distance+phi+theta, and the onSelect callback fires to surface the feature UI.

Lighting rig

  • HemisphereLight — sky colour → ground colour, intensity = ambient. Soft fill light, no shadows.
  • DirectionalLight (sun) — colour = sun, intensity = sunIntensity, casts shadows. 2048×2048 shadow map, 80-unit frustum, bias tuned to avoid shadow acne.
  • Sun direction — computed from azimuth + elevation every frame when the palette changes: sunDir.set(cos(az)*cos(e), sin(e), sin(az)*cos(e)).normalize()
  • Fog — THREE.Fog(palette.fog, 150, 500) — colour matches the horizon, density tuned per palette.

The sky shader blends topColor and bottomColor by vertical position, then tints the horizon by the sun direction — a cheap approximation of atmospheric scattering that reads well at the scale of a diorama.

Why palettes are data, not code: each palette is a plain Record<string, string|number>. To add a "monsoon" palette to any place, you add one entry to the TimeOfDay union, one object to the palette map, and one toggle in the UI. No shader code, no geometry code.

Data Layer: Dual-Driver Database

lib/store/db.ts is the single seam every data operation goes through. Three drivers, chosen at runtime from environment variables.

// lib/store/db.ts — driver abstraction
export type Database = {
  requests: PlaceRequest[];
  reviews:  Review[];
  views:    Record<string, number>;   // placeSlug → view count
};

type Driver = {
  read():  Promise<Database>;
  write(db: Database): Promise<void>;
};

// --- File driver (local dev, self-hosting) ---
function fileDriver(): Driver {
  return {
    read() {
      try {
        const raw = await fs.readFile(DB_FILE, 'utf8');
        return hydrate(JSON.parse(raw) as Partial<Database>);
      } catch (err) {
        if ((err as NodeJS.ErrnoException).code === 'ENOENT')
          return structuredClone(EMPTY);
        throw err;
      }
    },
    write(db) {
      await fs.mkdir(DATA_DIR, { recursive: true });
      // Atomic: write temp, then rename — crash-safe
      const tmp = `${DB_FILE}.${process.pid}.tmp`;
      await fs.writeFile(tmp, JSON.stringify(db, null, 2), 'utf8');
      await fs.rename(tmp, DB_FILE);
    },
  };
}

// --- Redis driver (Vercel production) ---
function redisDriver(credentials: { url, token }): Driver {
  const redis = new Redis(credentials);
  return {
    read() {
      return hydrate(await redis.get<Partial<Database>>(REDIS_KEY));
    },
    write(db) {
      await redis.set(REDIS_KEY, db);
    },
  };
}

// --- Unconfigured driver (Vercel without Redis) ---
function unconfiguredDriver(): Driver {
  return {
    read()  { return structuredClone(EMPTY); },
    write() { throw new Error(
      'No database configured. Connect a Redis store...'); },
  };
}

Driver selection logic

function activeDriver(): Driver {
  if (driver) return driver;
  const credentials = redisCredentials();
  if (credentials)      driver = redisDriver(credentials);
  else if (process.env.VERCEL) driver = unconfiguredDriver();
  else                   driver = fileDriver();
  return driver;
}

export function isPersistent(): boolean {
  return redisCredentials() !== null || !process.env.VERCEL;
}

Credential detection accepts both Vercel's injected KV_REST_API_* and Upstash's own UPSTASH_REDIS_REST_* names — so the app works whether the store was provisioned through the Vercel integration or directly.

Write queue

let writeQueue: Promise<unknown> = Promise.resolve();

export async function mutate<T>(
  mutator: (db: Database) => T | Promise<T>
): Promise<T> {
  const run = async () => {
    const store = activeDriver();
    const db    = await store.read();
    const result = await mutator(db);
    await store.write(db);
    return result;
  };
  const next = writeQueue.then(run, run);
  writeQueue = next.then(
    () => undefined,
    () => undefined,
  );
  return next;
}

Serialised writes: every mutate() call goes through a single promise chain, so two concurrent mutations in the same process can't interleave.

Trade-off acknowledged: across serverless instances (Vercel cold starts, multiple function invocations), the queue is per-instance — two instances can still race. At this app's write volume, the team has chosen simplicity over distributed consistency.

File Upload API: app/api/uploads/route.ts

// app/api/uploads/route.ts — multipart photo upload
export const runtime = 'nodejs';
export const dynamic = 'force-dynamic';

const UPLOAD_DIR      = path.join(process.cwd(), 'public', 'uploads');
const MAX_FILES       = 6;
const MAX_BYTES       = 4 * 1024 * 1024;   // 4 MB per photo
const EXT_BY_TYPE: Record<string, string> = {
  'image/jpeg': 'jpg',
  'image/png':  'png',
  'image/webp': 'webp',
  'image/gif':  'gif',
};

export async function POST(request: Request) {
  const form = await request.formData().catch(() => null);
  if (!form) return NextResponse.json(
    { error: 'Expected multipart form data' }, { status: 400 });

  const files = form.getAll('files')
    .filter((f): f is File => f instanceof File);

  if (files.length === 0)
    return NextResponse.json({ error: 'No files provided' }, { status: 400 });

  if (files.length > MAX_FILES)
    return NextResponse.json(
      { error: `Up to ${MAX_FILES} photos allowed` }, { status: 400 });

  // Validate everything before writing — no half-persisted batch
  for (const file of files) {
    if (!EXT_BY_TYPE[file.type])
      return NextResponse.json(
        { error: 'Only JPG, PNG, WEBP or GIF images are allowed' },
        { status: 400 });
    if (file.size > MAX_BYTES)
      return NextResponse.json(
        { error: 'Each photo must be under 4 MB' }, { status: 400 });
  }

  const useBlob = Boolean(process.env.BLOB_READ_WRITE_TOKEN);
  if (!useBlob) await fs.mkdir(UPLOAD_DIR, { recursive: true });

  const urls: string[] = [];
  for (const file of files) {
    const name = `${Date.now().toString(36)}-${randomUUID().slice(0, 8)}.${EXT_BY_TYPE[file.type]}`;
    if (useBlob) {
      const blob = await put(`uploads/${name}`, file, {
        access: 'public', contentType: file.type,
      });
      urls.push(blob.url);
    } else {
      await fs.writeFile(
        path.join(UPLOAD_DIR, name),
        Buffer.from(await file.arrayBuffer()));
      urls.push(`/uploads/${name}`);
    }
  }

  return NextResponse.json({ urls }, { status: 201 });
}

Design decisions

  • Multipart parsing on the server — no client-side upload library. The browser sends a FormData body, the route reads it.
  • Validate first, write second — the entire batch is validated before any file is persisted. A bad file late in the batch can't leave half the uploads on disk.
  • Dual storage — Vercel Blob (@vercel/blob put()) when BLOB_READ_WRITE_TOKEN is set; local /public/uploads/ otherwise. This keeps next dev and self-hosting working without a cloud account.
  • Filename: {timestamp-in-base36}-{uuid-slice}.{ext} — collision-resistant, sortable by time, no user data in the name.

Limits & known ceiling

  • A Vercel function request body maxes out at ~4.5 MB total. MAX_FILES × MAX_BYTES (6 × 4 MB = 24 MB) is not reachable in a single request on Vercel — the function would hit the body limit first. The constants are sized so dev/local uploads work fully, and Vercel uploads cap naturally at the function boundary.
  • Raising the ceiling requires a client-side upload (upload() from @vercel/blob/client) that streams past the function — a documented future upgrade.
  • Vercel Blob stores the file with access: 'public' — the returned URL is directly servable, no signed expiry.

function resolveSiteUrl(): string {
  if (process.env.NEXT_PUBLIC_SITE_URL)

Testing: Vitest on Pure Helpers

The project's tests live on the pure, canvas-free helpers — layout builders, zone predicates, anchor generators, palette functions. This is deliberate: WebGL is hard to test in a headless environment, so the architecture isolates the testable bits.

What's tested (examples)

// components/places/saras/baug-world.test.ts
// - buildSarasBaugLayout() returns the right prop count
// - markerBases match feature IDs
// - zone predicates (inBaug, inTemple) behave as expected

// components/places/dam/dam-world.test.ts
// - dam layout: wall, sluices, lake, chowpatty positions
// - terrain height field at known points

// components/places/memorial/memorial-world.test.ts
// - column height, flame position, vehicle placements

// components/places/pataleshwar/cave-world.test.ts
// - cave chamber dimensions, Nandi circle, linga position

// components/places/vetal/hill-world.test.ts
// - hill slope, shrine position, quarry pond bounds

Why this works

  • Layout helpers are pure functions — buildEmpressLayout(seed) returns a plain object. No THREE.Scene, no renderer. Vitest can call it and assert on the result.
  • Zone predicates are pure — inLawn(x, z) returns a bool. Test it at boundary points.
  • Anchor generators are pure — getEmpressAnchors() returns a record of plain arrays. Test that each feature id maps to an anchor.
  • Palettes are data — getEmpressPalette('dawn') returns a Palette object. Test that it's the right shape and values.

The WebGL path itself — createEmpressWorld(container, options) — is covered by the manual visual check: open the page, orbit, click hotspots, toggle modes. Automated canvas tests would be fragile and are not worth the maintenance cost at this stage.

// Running the suite
$ npx vitest run
  # → tests for layout builders, zone predicates, anchors, palettes

$ npx tsc --noEmit
  # → strict TypeScript across the whole project

$ npm run lint
  # → ESLint with eslint-config-next (Next.js 16 rules)
Test philosophy: if a function can be tested without a canvas, it should be. The 3D scene construction is the integration layer — tested by eye, not by assertion.

This layered model keeps the 3D worlds testable and replaceable — you can delete empress-world.ts and the data, story, and route all still compile. You can swap the DB driver without touching any component. You can add a new place by copying a folder and editing the data file — no import-chain surgery.

Performance Characteristics

Bundle & load

  • SSR shell: the server renders the cover, story, stats, etiquette, FAQs — pure HTML + CSS, no JS for the 3D. Fast first paint.
  • 3D chunk: createEmpressWorld and its dependencies are a client bundle loaded via next/dynamic. Only downloaded when the user reaches a place page and the component mounts.
  • three.js: bundled once (shared across all places). The per-place worlds add layout constants, prop specs, materials, and geometry builders — not a separate three.js for each place.
  • Asset size: zero external 3D assets. The entire visual world is generated from ~1000 lines of TypeScript per major place — no GLB, no texture download.

Rendering budget

  • Empress Garden: 1 plane (11,660 verts), 36 tree trunks + 108 canopy spheres (instanced), 42 rose blooms + 42 foliage (instanced), 1 greenhouse (box), 6 tents (cones), 4 lamps (cylinder + sprite), 4 benches (box). All in a single WebGLRenderer with PCFSoftShadowMap, ACESFilmicToneMapping, 2048×2048 shadow map.
  • Shadow draw: one directional light, one shadow camera (80-unit frustum). Trees and greenhouse cast shadows; ground receives.
  • Fog: distance-based, 150–500 units — hides the edges of the 120×116 ground plane.
  • Pixel ratio cap: Math.min(devicePixelRatio || 1, 2) — no 3× retina rendering.
Zero external 3D assets One three.js shared bundle ~12K vertices in Empress ground plane ~190 instanced objects (trees + roses + canopy layers) 3 palettes, switchable at runtime 0 textures (all material colours + vertex colours)
Rendering cost model: the scene is procedurally generated once on mount, then drawn every frame. No per-frame layout rebuild. The most expensive per-frame cost is the shadow map render (2048×2048, one light). On a modern phone this is smooth; on a low-end device, the pixel ratio cap and fog keep it tolerable. The powerPreference: 'high-performance' hint asks the browser for the fast path.

Known Limitations & Trade-offs

AreaLimitationWhy it's acceptable now
Cross-instance writes The write queue is per-process. Two Vercel function instances can race on mutate(). At this traffic level, the race window is tiny and the data (reviews, suggestions) is non-critical. A real Redis-based queue or Upstash QStash would be the next step if write volume grows.
Vercel Blob limit A single upload request cannot exceed ~4.5 MB total body on Vercel — so 6 × 4 MB is unreachable. Documented in the route. A client-side upload() from @vercel/blob/client would stream past the function. Not needed until users want to upload larger batches.
No audio No TTS or ambient audio in the 3D scenes yet. Sarvam TTS integration is a documented next step — the data layer already has Marathi names ready for voice.
No user accounts Reviews and suggestions are anonymous and stored in the shared DB document. No persistence across sessions (file driver resets on re-deploy; Redis persists but no user identity). Acceptable for a demo. User accounts would need an auth layer (NextAuth, Clerk, or similar) — a medium-term addition.
No mobile-specific 3D controls OrbitControls works on touch, but there's no two-finger zoom / one-finger orbit distinction tuned for mobile. The scenes work on mobile — touch orbit + scroll zoom function. Fine-tuning would be a polish pass, not a structural change.
Procedural = stylised The models are clearly "diorama" — not photoreal. Tree canopies are icosahedra, lamp flames are sprites, tents are cones with stripes. This is the design intent: a hand-built diorama feel, not a scan. It matches the editorial tone and keeps the bundle small.
No sitemap / SEO beyond metadata SITE.url is used for metadata, but there's no explicit sitemap.xml generation or structured data beyond the SITE constants. Next.js 16 has sitemap support via sitemap.ts — a small addition. Structured data (Place, TouristAttraction schema) would be a nice-to-have.
The one trade-off that matters most: the procedural approach trades visual realism for author speed and bundle size. Every place is a diorama, not a replica. For a heritage guide aimed at discovery and inspiration, this is the right call — but it's worth stating explicitly.

Deployment Topology

Vercel Production (explorepune.vercel.app) ├── Next.js 16 — App Router ├── SSR: place shell, directory, homepage (HTML + CSS, no 3D JS) ├── Client bundle: three.js + per-place worlds (loaded on demand) ├── Upstash Redis — KV_REST_API_URL / KV_REST_API_TOKEN │ └── Key: "explorepune:db" → { requests, reviews, views } ├── Vercel Blob — BLOB_READ_WRITE_TOKEN │ └── Public uploads/{timestamp}-{uuid}.{ext} ├── NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL → SITE.url └── Edge: closest to Pune → typically Mumbai / Singapore Preview Deployments (per branch/commit) ├── NEXT_PUBLIC_VERCEL_URL → SITE.url (self-consistent links) ├── Same Redis (shared) or unconfigured driver (reads empty, writes error) └── Fresh 3D bundles per deploy — no cache staleness Local Dev (next dev, port 3000/3001) ├── File driver → data/db.json (atomic write/rename) ├── Local uploads/ → /public/uploads/ ├── No Redis, no Blob — full functionality, no cloud account └── SSR off for 3D pages (ssr: false) — same as production Self-Host (next start, any Node host) ├── Same as local dev — file driver, local uploads ├── Set NEXT_PUBLIC_SITE_URL for correct metadata └── Add Redis credentials to enable persistent writes

Why Vercel works well here

  • Next.js 16 is first-class on Vercel — no custom server, no Dockerfile.
  • Upstash Redis is integrated via Vercel's KV — one credential pair, no separate Redis provisioning.
  • Vercel Blob is integrated the same way — upload token, no S3 bucket wrangling.
  • Preview deployments give every PR a live URL — useful for reviewing a new place's 3D scene before merging.

What would change for scale

  • Redis: at high write volume, a per-instance write queue isn't enough — move to a Redis-based queue (Upstash QStash, or a Redis list with LPUSH/BRPOP).
  • Blob: at high upload volume, switch to @vercel/blob/client upload() for streaming past the function body limit.
  • CDN: the 3D bundles are already served via Vercel's edge — no separate CDN needed until the bundle grows past a few hundred KB.
  • Region: if the audience shifts outside India, pin the Vercel project to a region closer to the new audience.

Architecture Summary

What we built

  • A Next.js 16 + React 19 web app that guides visitors through Pune's heritage.
  • 15 places, each with editorial depth (story, etiquette, FAQs, Marathi names) and a hand-built procedural 3D diorama.
  • A dual-driver data layer (Redis for production, file for dev) with serialised writes and fail-closed behaviour.
  • A file upload API (Vercel Blob or local) for community photos.
  • A per-place component architecture with a shared diorama core — each place is independently addable.

What makes it technically interesting

  • Procedural 3D at scale: 15 places, zero imported meshes, every vertex generated from TypeScript. This is unusual and cheap to extend.
  • SSR + client island split: the editorial content is server-rendered; the 3D is a dynamic import that only loads when needed.
  • Deterministic layouts: seeded PRNG means every world is reproducible — tests can assert on exact prop positions.
  • Environment-driven deployment: one codebase runs locally, on Vercel preview, and on Vercel production with the right driver for each — no branches, no env-specific code paths beyond the driver selection.
  • Testable 3D: the parts that matter (layout, anchors, palettes) are pure functions, tested without a canvas.
Next.js 16 (App Router) React 19 three.js 0.180 TypeScript strict Tailwind 4 + Base UI Vitest Upstash Redis + Vercel Blob Vercel deployment
The core idea, restated: ExplorePune is a city guide where every place is a diorama you can orbit, zoom, and fly through — built entirely from code, with editorial depth, and deployed for free on Vercel. The technical architecture supports adding more places without an art pipeline, without heavy assets, and without a backend beyond a Redis document store.
