The Problem We Solved

Pune is one of India's most culturally rich cities — yet discovering its heritage sites remains surprisingly difficult.

What travelers face today

  • Scattered information — no single source brings forts, temples, museums and gardens together
  • Static images only — photos don't convey scale, layout, or atmosphere
  • No visual preview — visitors can't "walk through" a place before committing time and effort
  • Frustrating planning — finding opening hours, entry fees, best visiting seasons requires jumping across blogs and forums

What locals miss

  • Hidden gems like Pataleshwar Cave Temple or Khadakwasla Dam's radial sluices are underserved by mainstream content
  • Seasonal context — the difference between Empress Garden on a Tuesday vs. during the January flower show is enormous, but never visualised
  • No community layer — no easy way to suggest a place or read real visitor experiences
ExplorePune turns Pune's heritage into a visual, interactive, curated destination — on the web, for free, in one place.

What Is ExplorePune?

A web-based city guide that combines editorial depth with hand-built 3D experiences for every place it covers.

What makes it different

  • Procedural 3D dioramas — every place is a hand-built three.js scene, generated at runtime. Zero imported GLB files.
  • Hotspot navigation — tap numbered stops to fly the camera and read the story behind each landmark.
  • Time-of-day & season modes — switch between dawn, golden hour, and dusk. Toggle festival mode where it matters.
  • Marathi + English — feature names are bilingual, grounded in local language.

How a Visitor Uses ExplorePune

The experience is designed to move a user from discovery to decision in under a minute.

1. Discover

Land on the homepage. Browse category tiles (Forts, Temples, Gardens, Museums, Lakes & Hills). See featured places ranked by rating. Scroll through curated collections.

2. Filter & Search

On the Places page, filter by category, area, audience type, season, or free/paid entry. Switch between grid, list, and Google Maps views. Search by keyword.

3. Explore in 3D

Open any place. Drag to orbit the 3D scene. Scroll to zoom. Tap a numbered hotspot — the camera flies there, and the editorial story loads: history, architecture, what to see, etiquette, FAQs.

4. Plan the Visit

Every place guide includes: how to reach it, visitor tips, nearby places, and practical essentials. Users leave reviews (stored locally for the demo) and suggest missing places through a community form.

Every 3D page keeps WebGL out of the server render — using next/dynamic with ssr: false — so the first paint is fast and the canvas only loads client-side.

Our 3D Strategy: Why Procedural?

This is the single most important technical decision in ExplorePune — and the one with the biggest business implications.

The conventional approach

  • Model every place in Blender → export GLB → load with useGLTF
  • Cost: an artist per place, days of work each
  • Size: each GLB adds 50 KB–2 MB to the bundle
  • Iterate: changing a wall colour means re-exporting from a 3D tool
  • Scale: 15 places = significant Art/3D budget

ExplorePune's approach

  • Write pure TypeScript: geometry primitives, instanced meshes, procedural layout, custom materials
  • Cost: one developer, no art pipeline
  • Size: zero external 3D assets — everything generated at runtime from code
  • Iterate: adjust a tree count or rose-ring radius by editing a number in a helper
  • Testable: layout helpers and camera anchors are pure functions — tested with Vitest, no WebGL needed
36 Trees in Empress Garden (procedural)
42 Rose bushes across 3 concentric rings
6 Flower-show tents, toggleable by mode
3 Time-of-day palettes (dawn, golden, dusk)
Example: Empress Garden's buildEmpressLayout(seed = 1892) generates 36 old-growth trees, 42 rose bushes, a greenhouse, benches, lamps, and 6 flower-show tents — all from deterministic seeded random placement. Change the seed, change the layout. No artist involved.

Inside a Place Page

Every place follows the same component architecture — consistent UX, isolated implementation per site.

Component breakdown

  • place-cover.tsx — hero image area, category badge, key metadata
  • place-detail.tsx — the shell that composes the story, 3D experience, and practical info
  • *-story.tsx — the editorial content: headings + body paragraphs (e.g. empress-story.tsx)
  • *-world.ts — the procedural 3D world: layout, anchors, palette, create*-World() factory (e.g. empress-world.ts, 1032 lines for Empress alone)
  • *-experience.tsx — the React bridge: next/dynamic import, canvas container, controls, mode switches
  • *-scene.tsx — scene-level setup that calls into the world module

What's in the data file

  • Features — each hotspot id, title, Marathi name, icon, blurb, and full detail paragraph (e.g. EMPRESS_FEATURES has 5 features)
  • Stats — labelled facts (39 acres, since 1892, January show)
  • Story — 2–3 narrative sections with headings
  • Etiquette — visitor do's and don'ts
  • FAQs — 4–5 questions with grounded answers

The feature ids in the data file double as hotspot ids in the 3D scene — one source of truth.

Design principle: each place owns its own folder under components/places/ — empress/, saras/, dam/, memorial/, etc. No shared 3D code between places except the core diorama helpers in components/places/three/diorama-core.ts.

Data Layer & Infrastructure

Database abstraction (lib/store/db.ts)

A tiny JSON document store that exposes requests, reviews, and views. Two drivers, chosen at runtime:

  • Redis driver — when KV_REST_API_URL + token are present (Vercel deployment). Uses Upstash Redis REST API. Key: explorepune:db.
  • File driver — on-disk data/db.json. Atomic writes via write-then-rename to prevent corruption on crash.
  • Unconfigured driver — Vercel-only fallback: reads return empty, writes throw a clear error pointing to DEPLOYMENT.md.

Write operations are serialised through a promise queue to avoid interleaving within one process.

File upload API (app/api/uploads/route.ts)

  • Multipart form, field name files
  • Up to 6 photos per request, 4 MB each
  • Accepted types: JPG, PNG, WEBP, GIF
  • Cloud path: @vercel/blob with BLOB_READ_WRITE_TOKEN → public URLs
  • Local path: /public/uploads/ for next dev and self-hosting
  • Deploys cleanly on Vercel; falls back to local disk in dev

Environment-driven config

NEXT_PUBLIC_SITE_URL overrides the base URL for metadata. Falling back to Vercel-injected NEXT_PUBLIC_VERCEL_PROJECT_PRODUCTION_URL ensures preview deploys never advertise localhost.

Deployment & Operations

How it's deployed

  • Platform: Vercel — zero-config Next.js deployment, auto SSL, global edge network
  • Production URL: https://explorepune.vercel.app
  • Preview deployments: every push to a branch gets a unique URL, powered by Vercel's per-deployment NEXT_PUBLIC_VERCEL_URL
  • Region: Vercel's default — closest edge to Pune visitors is typically Mumbai or Singapore

Dev experience

  • npm install → npm run dev — starts on port 3000 (or 3001 if taken)
  • npm run typecheck — strict TypeScript check
  • npm test — Vitest run, tests layout/anchor helpers
  • npm run build — full production build, including 3D worlds as client bundles
  • npm run lint — ESLint with Next.js config
